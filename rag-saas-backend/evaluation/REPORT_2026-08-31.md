B supplied four contexts for q04, q07 and q08, and eight for the other queries.
A always supplied eight. On the answerable subset the mean counts are A=8 and B=7.
With equal context counts for each query, gold chunk precision is
**0.322917 → 0.364583**. Hit rate remains **10/12 → 12/12**. This sensitivity check
is retrieval-only; the main RAGAS comparison measures the combined effect of
production scoring, filtering, ordering and context count, not sorting alone.

Exhaustive chunk recall counts all 35 equivalent housekeeping pages for the two
generic housekeeping questions. Evidence-group recall instead measures whether
the necessary fact is available at least once; it is the more useful coverage
interpretation for those questions. Neither metric is RAGAS Context Recall.

All four unanswerable questions received the exact production refusal in both
arms: **4/4 each**. Their Answer Relevancy values are zero, as expected for that
metric's treatment of noncommittal answers; this does not make a correct refusal
incorrect. Their Context Precision was predeclared not applicable, and all eight
of their Faithfulness calls were quota-blocked.

For both questions, A answered “I cannot answer this based on the provided
document.” B correctly identified shelf 27 and shelf 31, respectively, from the
promoted pages. Full text, stable chunk IDs, CrossEncoder scores and ranks are in
the per-query JSON and `candidate_ranks.csv`.

Every answerable query's required evidence was already present in the shared
MMR candidates. No labeled relevant chunk was absent from the vector pool or MMR
list. Thus **reranking promoted evidence omitted by the baseline's final-context
cutoff; it did not recover evidence missing from vector retrieval**. In q10 the
needed page was already vector rank 8 before MMR moved it to rank 19.

The two housekeeping questions also had relevant pages exchanged/promoted, but
they already had usable evidence in A. Those exchanges are not counted as newly
successful questions. All promotions and losses remain in the raw traces.

## Judge limitations that constrain resume wording

The completed metric values above are genuine RAGAS outputs, not corrected or
selected to match a target. Offline verification found **five unique
query/chunk Context Precision disagreements** against the frozen labels:

- q05: the judge rejected the Aurora code chunk because it supplied only half
  the two-station answer, while accepting the Borealis code chunk for supplying
  the other half. Identical query/chunk judgments were shared across arms.
- q06 and q07: it rejected each of the two required station-information chunks
  for individually lacking the whole comparative answer. Both final contexts
  contained the necessary evidence, but RAGAS Context Precision was zero.

Faithfulness also has inspectable artifacts. For q08/B, the correct answer
“No, the maintenance access codes are not real credentials” was split into the
supported claim and the extra statement “The answer to the question is no.” The
second statement was rejected, producing 0.5. For q09/A, a proper refusal given
its missing evidence was partly penalized because the context contained other,
unrelated information. q10/A's refusal received zero.

Therefore the measured Faithfulness increase is **not convincing evidence of
reduced hallucination**. Context Precision is also a fallible judge-derived
ranking measure; it is not the proportion of chunks that are relevant. Use the
frozen gold labels and rank traces for the stronger retrieval conclusion.
Answer Relevancy is secondary: for example, both q04 answers were the correct
“29 days,” but the judge generated the vague question “How many days?”, yielding
0.404880. It is not an answer-correctness metric.

## Resume claims: what is defensible now?

| Resume claim | Status | Evidence and defensible correction |
| --- | --- | --- |
| Document-grounded PDF RAG using 384-dimensional HuggingFace embeddings | Supported | Real PDFs produced 72 chunks and actual stored/query vectors of length 384; production ingestion and generation services ran. |
| MMR retrieval over 40 candidate chunks | Needs correction | Global queries used 60 vector candidates and returned 40 MMR selections. Filtered queries had only 36 available chunks. Say “MMR selecting up to 40 chunks from up to 60 vector candidates.” |
| Metadata filtering and CrossEncoder top-8 reranking | Supported with qualification | Filename filters were preserved; the actual CrossEncoder scored the shared MMR list. Say “up-to-eight context chunks”; three questions received four. |
| Per-query RAGAS diagnosis of retrieval quality | Supported as newly implemented work | Paired per-query metrics, references, ranks and gold labels now exist. Judge anomalies and the missing scores must remain disclosed; this does not establish historical diagnosis. |
| Reranking recovered relevant chunks missed by vector retrieval | Unsupported literally | All required evidence was already in the retrieved candidate sets. Supported wording: “promoted relevant chunks omitted from the baseline final context,” with q09/q10 traces. |
| Faithfulness 0.72 → 0.87 | Unsupported | No historical reproducible evidence; the new partial paired measurement is 0.863636 → 0.954545 over 11 pairs, with judge anomalies. Do not reuse the old figures or present the new ones as general performance. |
| Context Precision 0.64 → 0.81 | Unsupported | The new complete synthetic measurement is 0.568226 → 0.791667 over 12 answerable pairs, with five label disagreements. This does not reproduce or validate the old figures. |

Safer resume wording:

> Built document-grounded PDF QA with 384-dimensional MiniLM embeddings,
> filename-filtered Qdrant retrieval, MMR selecting up to 40 of 60 candidates,
> and CrossEncoder reranking to up to eight context chunks.

> Implemented paired RAGAS evaluation with per-query chunk-rank traces; on a
> 12-query synthetic answerable benchmark, reranking promoted two omitted
> evidence chunks into the final context, increasing evidence hit rate from
> 83.3% to 100%.

The synthetic qualifier is essential. A larger frozen real-document corpus and
better-established judge validity would be needed for a broad quality claim.

## Execution, failures and validation

The first pass is `20260831_synthetic_stations_v1_01`. It generated **32/32 answers**
and completed **79/88 applicable metric scores**: 23 Faithfulness, 24 Context
Precision and 32 Answer Relevancy. The other eight metric slots are deliberately
not-applicable Context Precision entries for unanswerable questions.

q12/B Faithfulness failed with HTTP 429 after exhausting retries at the observed
8,000-token/minute limit. The eight unanswerable Faithfulness scores then failed
at the 200,000-token/day limit. Their JSON/CSV values are null/blank with explicit
`failed` status, never fabricated zeroes. The command exited nonzero and metadata
says `completed_with_failures`.

`20260831_synthetic_stations_v1_01_recovery01` preserves a recovery attempt using
the identical inputs, answers, judge settings and successful cache entries.
Retrying q12/B again hit the daily quota, so recovery stopped immediately. All
successful metrics and aggregate values were verified unchanged, and the original
failure remains in `prior_attempts`. This is not an independent second experiment.
Finishing the nine missing values requires available quota for the same judge.

Validation completed:

- Offline replay reproduced all 16 vector candidate lists, scores and MMR orders
  from the archived vectors using the pinned embedded Qdrant version.
- Artifact verification recomputed all 24 completed Context Precision scores,
  23 Faithfulness scores and 32 Answer Relevancy scores; checked gold labels,
  threshold/top-N selections, actual prompts, CSV/JSON agreement and aggregates.
- All 14 production Python source files matched their hashes at run start.
  Frontend files were unchanged. No production retrieval or generation tuning.
- All five existing tests passed against a separate empty local Qdrant collection
  after the dependency pin; `pip check` passed. No Phase 4 tests were added.

RAGAS 0.4.3 initially could not import because LangChain Community 0.4.2 removed
its referenced VertexAI module. The evaluation requirements pin Community 0.4.1;
the new runner uses real RAGAS classes, without the legacy evaluator's fake-module
workaround. The complete package snapshot is saved with each run.

Models/configuration: `all-MiniLM-L6-v2`, revision
`1110a243fdf4706b3f48f1d95db1a4f5529b4d41`; CrossEncoder
`cross-encoder/ms-marco-MiniLM-L-6-v2`, revision
